# Pi0 OM Inference Debug Experience

This document records common problems and troubleshooting paths when Pi0 performs ONNX export, ATC-to-OM conversion, OM accuracy verification, and end-to-end inference on the Ascend 310P. It is recommended to first complete the basic environment preparation following the [Pi0 OM Inference Usage Guide (Chinese)](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/README.md), and then use this document to locate problems section by section.

## 1. First Fix the Troubleshooting Boundaries

For the Pi0 OM pipeline, it is recommended to fix the following prerequisites; otherwise, many errors will manifest as configuration, shape, or weight-loading problems:

- Use LeRobot code version `577cd10974b84bea1f06b6472eb9e5e74e07f77a`.
- The model directory should contain `config.json`, weight files, and tokenizer-related files.
- Use the same set of Pi0 adaptation files for ONNX export and OM verification.
- Export the VLM and the action expert separately; the action expert depends on the intermediate tensors saved during the VLM export stage.
- For a custom model, confirm that `config.json.input_features`, `config.json.output_features`, and `chunk_size` are consistent with the actual data.

Minimal directory check:

```bash
ls /path/to/pi0_model/config.json
ls /path/to/cann-recipes-embodied-ai/manipulation/pi0/infer_with_om/lerobot_modify/
ls /path/to/cann-recipes-embodied-ai/manipulation/pi0/infer_with_om/lib/modeling_gemma.patch
```

## 2. Why Split into Two OM Segments

The Pi0 inference chain consists of two parts:

- VLM module: processes images, language, and body state, and generates prefix features and the KV cache.
- Action expert module: based on the KV cache and action noise generated by the VLM, performs multi-step denoising and outputs the action sequence.

This sample does not export the complete Pi0 into a single OM at once; instead, it is split into two segments: the VLM and the action expert:

- Reduces the memory overhead of the ATC tool during conversion. The complete Pi0 graph includes the vision encoder, language/image prefix processing, the KV cache, and multi-step action expert denoising. The overall graph is large, and converting it all at once is more likely to trigger memory pressure or compilation failure.
- Fixes the boundary of the intermediate tensors output by the VLM. The VLM segment outputs `past_kv_tensor` and `prefix_pad_masks`, and the action expert segment takes them as explicit inputs, which helps verify the ONNX/OM accuracy of the two model segments independently.
- Makes problem localization easier. If the VLM segment verifies normally but the action expert segment is abnormal, you can directly focus on the KV cache, attention mask, position ids, or action post-processing, without mixed troubleshooting in the complete end-to-end graph.
- Reuses the Pi0 inference structure. Pi0's original inference itself first computes the image/language prefix KV cache and then performs multi-step denoising in the action expert; the two-segment OM preserves this boundary.

Corresponding files:

- [modeling_pi0_vlm.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/lerobot_modify/modeling_pi0_vlm.py): exports the VLM prefix encoding graph and outputs `past_kv_tensor` and `prefix_pad_masks`.
- [modeling_pi0_action_expert.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/lerobot_modify/modeling_pi0_action_expert.py): exports the single-step denoising graph of the action expert, taking the KV cache generated by the previous segment as input.
- [run_om_e2e.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/run_om_e2e.py): connects the two OM segments end to end and calls the action expert in a loop.

## 3. Major Operator and Logic Modifications

The goals of the Pi0 OM version and the Ascend torch inference optimization version are different:

- The torch inference optimization version prioritizes `torch_npu` fused operators to improve runtime performance.
- The OM version prioritizes the stability of ONNX export, ATC compilation, and OM Runtime verification, so some fused operators are changed back to basic operator combinations that are easier to export and compile.

### 3.1 KV Cache Flattening

In the original inference, `past_key_values` is usually a Python list/dict structure. ONNX/OM is not suitable for directly expressing such nested objects, so the OM version flattens it into a single Tensor:

```text
list[{"key_states": Tensor, "value_states": Tensor}]
-> Tensor(L, 2, B, S, H, D)
```

Related functions:

- `flatten_kv`
- `unflatten_kv`

This allows the output of the VLM OM to be used directly as the input of the action expert OM.

### 3.2 RoPE Rotary Encoding

In the Ascend torch inference optimization version, the following can be used:

```python
torch_npu.npu_rotary_mul(...)
```

In the OM version, this is changed to an ONNX-friendly hand-written RoPE:

```python
sin = torch.sin(radians)
cos = torch.sin(radians + math.pi / 2)
res[..., :d_half] = x1 * cos - x2 * sin
res[..., d_half:] = x2 * cos + x1 * sin
```

Reasons:

- `npu_rotary_mul` is suitable for NPU eager/graph inference optimization, but not necessarily suitable for the current ONNX export and ATC compilation path.
- The hand-written version consists of basic operators and is easier to align in ONNX/OM accuracy.
- Using `sin(x + pi/2)` to express cos reduces inconsistencies caused by cos precision or export differences in some environments.

### 3.3 Attention

In the Ascend torch inference optimization version, the following can be used:

```python
torch_npu.npu_prompt_flash_attention(...)
```

In the OM version, this is changed to basic attention computation:

```python
att_weights = torch.matmul(query_states, key_states.transpose(2, 3))
att_weights *= head_dim**-0.5
masked_att_weights = torch.where(attention_mask[:, None, :, :], att_weights, big_neg)
probs = nn.functional.softmax(masked_att_weights, dim=-1)
att_output = torch.matmul(probs, value_states.permute(0, 2, 1, 3))
```

Reasons:

- `npu_prompt_flash_attention` is a runtime fused operator suitable for performance optimization on the torch_npu path.
- OM export focuses more on ATC compilability and input/output stability; basic attention makes it easier to troubleshoot mask, shape, and dtype problems.
- The attention mask shapes of the VLM segment and the action expert segment differ, and the basic implementation is more convenient for separate verification.

### 3.4 RMSNorm and Residual Add

In the Ascend torch inference optimization version, the following can be used:

```python
torch_npu.npu_rms_norm(...)
torch_npu.npu_add_rms_norm(...)
```

In the OM version, ordinary module calls and explicit residuals are used:

```python
hidden_states = layer.input_layernorm(hidden_states)
out_emb = layer.self_attn.o_proj(att_output[:, start:end])
out_emb += hidden_states
after_first_residual = out_emb.clone()
out_emb = layer.post_attention_layernorm(out_emb)
out_emb = layer.mlp(out_emb)
out_emb += after_first_residual
```

Reasons:

- Fused RMSNorm/add operators are more performance-friendly for torch_npu.
- Keeping the ordinary operator combination during OM export is more conducive to segment-by-segment alignment of ONNXRuntime and OM outputs.
- The explicit residual path makes it easier to locate errors caused by layernorm, MLP, or dtype.

### 3.5 dtype, Mask, and Position IDs

On the OM path, special attention must be paid to dtype:

- Image and state inputs to the VLM are usually kept in `float32`.
- state, KV, time, and noise in the action expert mostly use `float16`.
- `lang_tokens` uses `int64`.
- `lang_masks` and `prefix_pad_masks` use bool.
- Before `cumsum`, the mask must be explicitly converted to an integer type, then converted back to bool to participate in mask computation.

Reasons:

- NPU/ATC is more sensitive to certain dtype combinations, and implicit type conversions can easily make the exported graph unstable.
- The attention mask and position ids are the places where the two OM segments are most likely to have shape/dtype inconsistencies.
- Explicit dtype reduces input differences between ONNXRuntime and OM Runtime.

## 4. LeRobot Version or Patch Inconsistency

Symptoms:

- `PI0Policy.from_pretrained` reports missing config fields when loading.
- `modeling_pi0_vlm` or `modeling_pi0_action_expert` cannot be imported.
- Errors related to input fields, model structure, or tokenizer occur during the ONNX export stage.

Handling:

1. Confirm the LeRobot commit:

```bash
cd /path/to/lerobot
git rev-parse HEAD
```

2. Confirm that the Pi0 OM adaptation files have been copied:

```bash
export LEROBOT=/path/to/cann-recipes-embodied-ai/manipulation/lerobot
export INFER_WITH_OM=/path/to/cann-recipes-embodied-ai/manipulation/pi0/infer_with_om

cp "$INFER_WITH_OM/lerobot_modify/modeling_pi0_vlm.py" "$LEROBOT/src/lerobot/policies/pi0/"
cp "$INFER_WITH_OM/lerobot_modify/modeling_pi0_action_expert.py" "$LEROBOT/src/lerobot/policies/pi0/"
cp "$INFER_WITH_OM/lerobot_modify/paligemma_with_expert_fp16.py" "$LEROBOT/src/lerobot/policies/pi0/"
cp "$INFER_WITH_OM/lerobot_modify/normalize.py" "$LEROBOT/src/lerobot/policies/"
```

3. Confirm that the Gemma patch for `transformers` can be applied:

```bash
cd /path/to/conda/envs/lerobot/lib/python3.10/site-packages/transformers/models/gemma
git apply --check -p1 "$INFER_WITH_OM/lib/modeling_gemma.patch"
git apply -p1 "$INFER_WITH_OM/lib/modeling_gemma.patch"
```

If `git apply --check` fails, it is not recommended to continue the export. First confirm the current `transformers` version and the patch adaptation relationship.

## 5. Hugging Face Model Download or Gated Model Problems

Symptoms:

- Downloading `google/paligemma-3b-pt-224` times out, returns 403, or gets stuck.
- In an offline environment, the startup still attempts to access Hugging Face.

Handling:

- First download the model on a machine with network access, then copy the model directory to the runtime environment.
- If a mirror must be used, you can temporarily set `HF_ENDPOINT=https://hf-mirror.com`.
- `google/paligemma-3b-pt-224` is a gated model, and access authorization must be completed in advance on the Hugging Face page.
- In an offline environment, replace the hard-coded `google/paligemma-3b-pt-224` in the LeRobot code with a local path; the README lists the involved locations.

It is recommended to prioritize the local path to reduce network variables during export and verification.

## 6. Action Expert Export Missing `runtime_save`

Symptoms:

- [convert_verify_onnx_action_expert.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/convert_verify_onnx_action_expert.py) reports that `past_kv_tensor.pth` or `prefix_pad_masks.pth` does not exist.
- Running the action expert export alone fails.

Cause:

The Pi0 OM pipeline is split into two segments:

- The VLM export stage generates `runtime_save/past_kv_tensor.pth` and `runtime_save/prefix_pad_masks.pth`.
- The action expert export stage needs to read these two files to reuse the intermediate features and masks consistent with the VLM.

Handling:

```bash
cd /path/to/cann-recipes-embodied-ai/manipulation/pi0/infer_with_om

./run_pi0_export.sh \
  --pretrained-policy-path /path/to/pi0_model \
  --runtime-save-dir runtime_save

ls runtime_save/past_kv_tensor.pth
ls runtime_save/prefix_pad_masks.pth
```

If you need to run the steps separately, first run [convert_verify_onnx_vlm.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/convert_verify_onnx_vlm.py), then run `convert_verify_onnx_action_expert.py`, and make sure both steps use the same `--runtime-save-dir`.

## 7. ONNX Export Succeeds but ATC Conversion Fails

Symptoms:

- ATC compilation reports errors related to operators, shape, dtype, or `soc_version`.
- After the OM is generated, execution reports `acl.mdl.execute error 507011`.

Troubleshooting order:

1. Confirm the device model:

```bash
npu-smi info
```

2. Confirm that the `--soc_version` used by ATC is consistent with the device. For example, if the device is a 310P1, use:

```bash
--soc_version=Ascend310P1
```

3. Keep the precision configuration in the README:

```bash
--precision_mode_v2=origin
```

4. Confirm the ONNX file path and output name. ATC's `--output=outputs/om/pi0_vlm` generates `outputs/om/pi0_vlm.om`; subsequent scripts should use the actually generated file name.

If the model, input resolution, or action dimensions are changed, you need to re-export the ONNX and then re-run the ATC conversion. Do not reuse the old OM.

## 8. ACL / AclLite Dependencies Not Found

Symptoms:

- `import acl` fails.
- `acllite_utils` or `acllite_model` cannot be found.
- The OM verification script fails at startup.

Handling:

```bash
source /path/to/Ascend/ascend-toolkit/set_env.sh
export PYTHONPATH=/path/to/Ascend/ascend-toolkit/latest/thirdpart/python/:$PYTHONPATH
```

If the path is uncertain, you can search for it on the machine:

```bash
find /path/to/Ascend -name acllite_utils.py
```

`PYTHONPATH` should point to the parent directory of the directory containing `acllite_utils.py`, or to a directory from which it can actually be imported.

## 9. ONNX and OM Accuracy Inconsistency

Symptoms:

- [verify_om_onnx_vlm.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/verify_om_onnx_vlm.py) or [verify_om_onnx_action_expert.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/verify_om_onnx_action_expert.py) outputs large `max_abs_error` and `mean_abs_error`.
- `prefix_pad_masks mismatches` is not 0.
- The end-to-end output actions of the OM are clearly abnormal.

Prioritize checking dtype and input order:

- In the VLM inputs, image and state use `float32`, `lang_tokens` use `int64`, and `lang_masks` use bool.
- In the action expert inputs, state, `past_kv_tensor`, `time`, and `noise` use `float16`, tokens use `int64`, and mask uses bool.
- The OM input order must be consistent with the ONNX input order. The verification script first reads the ONNX input order, then feeds it to the OM in the same order.

It is recommended to first verify the two segments separately:

```bash
python3 verify_om_onnx_vlm.py \
  --onnx-model-path outputs/onnx/pi0-vlm.onnx \
  --om-model-path outputs/om/pi0_vlm.om

python3 verify_om_onnx_action_expert.py \
  --onnx-model-path outputs/onnx/pi0-action_expert.onnx \
  --om-model-path outputs/om/pi0_action_expert.om \
  --past-kv-path runtime_save/past_kv_tensor.pth \
  --prefix-mask-path runtime_save/prefix_pad_masks.pth
```

If the VLM accuracy is normal but the action expert is abnormal, focus on checking whether `runtime_save` comes from the same VLM export, and whether the action expert's `--lang-len` and `--noise-shape` are consistent with those at export time.

## 10. End-to-End Action Output Abnormal

Symptoms:

- `run_om_e2e.py` can run, but the action range is clearly abnormal.
- In simulation, the robot actions jitter, have unreasonable amplitudes, or fail to complete tasks.

Common causes:

- When using a custom model, the corresponding action normalization statistics are not provided.
- `output_features.action.shape` is inconsistent with that at model training time.
- When the action dimensions are truncated from 32 to 14, the mapping is inconsistent with the target robot's degrees of freedom.

Handling:

If the example model in the README is used, you can directly use the default mean/std in the script. If a custom model is used, provide the action statistics saved during training:

```bash
python ./run_om_e2e.py \
  --mean-path /path/to/mean.pt \
  --std-path /path/to/std.pt \
  --vlm-model-path ./outputs/om/pi0_vlm.om \
  --action-expert-model-path ./outputs/om/pi0_action_expert.om
```

If the robot or action dimensions are changed, you should not rely only on the default `_to_action_14` truncation logic; you need to check the mapping according to the actual degrees of freedom and action key.

## 11. Simulation Evaluation Environment Problems

Symptoms:

- The MuJoCo / Aloha environment cannot start.
- Rendering fails in a headless environment.
- The evaluation script attempts to download models or environment dependencies over the network.

Handling:

```bash
export MUJOCO_GL=osmesa
```

If the system lacks OSMesa:

```bash
sudo apt-get install libosmesa6 libosmesa6-dev
```

During evaluation, use local model paths as much as possible and prepare dependencies in advance. When there is no GPU rendering requirement, OSMesa is a more stable choice.

## 12. Recommended Troubleshooting Order

When problems are encountered, it is not recommended to run the full simulation directly; instead, narrow down the scope in the following order:

1. Check the LeRobot commit, the `transformers` patch, and the Pi0 adaptation files.
2. Use a local model path to load `PI0Policy.from_pretrained`.
3. Run the VLM ONNX export and confirm that `runtime_save` is generated.
4. Run the action expert ONNX export and confirm that the ONNXRuntime comparison passes.
5. Use ATC to generate the VLM and action expert OMs separately.
6. Run the ONNX vs. OM verification scripts separately.
7. Run `run_om_e2e.py` to check the end-to-end action output.
8. Finally, integrate [eval_pi0_ascend.py](https://gitcode.com/cann/cann-recipes-embodied-ai/blob/master/manipulation/pi0/infer_with_om/eval_pi0_ascend.py) or the actual simulation environment. `eval_pi0_ascend.py` connects the VLM OM and action expert OM based on the LeRobot eval flow and can be used for Aloha simulation evaluation; other simulations or real-robot closed loops require further adaptation according to the environment interfaces.

In this way, the problem can be located in a specific segment among "environment/weight loading", "ONNX export", "ATC compilation", "OM Runtime", or "action post-processing", avoiding mixed troubleshooting in end-to-end simulation.
